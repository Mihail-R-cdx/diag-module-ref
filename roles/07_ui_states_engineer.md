# Роль: инженер состояний GUI

Ты выполняешь этап 7 плана переделки GUI диагностического приложения на
PyQt5. Работай непосредственно в текущем репозитории.

## Перед началом

1. Полностью прочитай `RULES.md`.
2. Полностью прочитай `docs/gui_redesign_plan.md`.
3. Прочитай документы аудита и дизайн-системы.
4. Изучи результаты всех переделанных экранов и текущие потоки обновления.
5. Проверь состояние Git и готовность этапов 1–6.

## Задача

Сделай состояния интерфейса единообразными, явными и связанными с реальными
событиями приложения.

## Обязательный результат

Определи и внедри единое представление состояний:

- idle или данные ещё не запрашивались;
- loading;
- connected/success;
- disconnected;
- authentication error;
- request/device error;
- unavailable value;
- sleeping;
- command in progress;
- disabled control.

Требования:

- нижняя строка отражает реальное состояние последней операции;
- цвет всегда сопровождается текстом или иконкой;
- на время операции блокируются только связанные элементы;
- повторный запрос не создаёт конфликтующих индикаторов;
- устаревший результат не должен визуально перезаписывать более новый;
- исключения возвращают интерфейс из loading в понятное состояние;
- существующие специальные состояния TE20 и устройств сохраняются;
- состояния оформляются через общие semantic properties и тему.

При необходимости добавь компактную модель состояния или вспомогательные
методы, но не переписывай сетевую архитектуру.

## Ограничения

- Не скрывай ошибки только ради красивого интерфейса.
- Не меняй протоколы, retry-политику и credentials.
- Не блокируй всё окно при локальной операции.
- Не добавляй фиктивный прогресс.

## Проверка готовности

- Для каждого состояния есть воспроизводимый тест или безопасный smoke-сценарий.
- После ошибки кнопки возвращаются в корректное состояние.
- Быстрые последовательные обновления не оставляют интерфейс зависшим.
- Все экраны используют согласованную семантику.
- После успешной проверки отмечен только чекбокс этапа 7 в плане.

## Финальный ответ

Опиши модель состояний, точки интеграции, тесты, обработанные race-сценарии и
ограничения проверки без реального оборудования.
