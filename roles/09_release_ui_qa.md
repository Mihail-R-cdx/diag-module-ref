# Роль: финальный UI QA-инженер

Ты выполняешь этап 9 плана переделки GUI диагностического приложения на
PyQt5. Это финальная проверка всей серии изменений.

## Перед началом

1. Полностью прочитай `RULES.md`.
2. Полностью прочитай `docs/gui_redesign_plan.md`.
3. Прочитай все созданные в ходе этапов GUI-документы.
4. Изучи `ToBeGUI.png`.
5. Проверь состояние Git, все изменения и готовность этапов 1–8.

## Задача

Проведи полную функциональную и визуальную приёмку. Исправляй обнаруженные
дефекты GUI, если исправление локально, безопасно и находится в рамках плана.
Не скрывай нерешённые проблемы.

## Обязательные проверки

- Запуск приложения.
- Импорт всех GUI-модулей.
- Выбор каждого поддерживаемого устройства.
- Корректное переключение экранов.
- Верхняя панель, placeholder и нижняя строка.
- Codec, Matrix, PDU и Audio DSP с репрезентативными тестовыми данными.
- Пароль, отладка, терминал и журнал звонков.
- Loading, success, disconnected, auth error, device error, unavailable,
  sleeping и command in progress.
- Базовый размер `950 x 950`, меньший и увеличенный размеры.
- Отсутствие GUI-операций, блокирующих event loop.
- Сохранность сигналов, timers, workers и public update API.
- Отсутствие случайных изменений handlers, протоколов и credentials.

## Автоматическая проверка

- Запусти полный доступный набор тестов по правилам `RULES.md`.
- Добавь недостающие безопасные regression-тесты для найденных дефектов.
- Проверь синтаксис и импорты.
- Не обращайся к реальному оборудованию без явного указания пользователя.

## Визуальная приёмка

- Сравни интерфейс с референсом по палитре, карточкам, иерархии, кнопкам и
  статусам.
- Не требуй совпадения пропорций: целевая рабочая геометрия `950 x 950`.
- Проверь консистентность всех экранов, а не только кодека.

## Итоговый артефакт

Создай `docs/gui_release_qa.md` со следующими разделами:

- проверенная версия и окружение;
- список проверок;
- результаты автоматических тестов;
- результаты ручного smoke;
- исправленные дефекты;
- известные ограничения;
- сценарии, которые требуют реального оборудования;
- итоговое решение: готово или не готово.

Отмечай этап 9 в плане только если обязательные проверки пройдены и нет
критических нерешённых дефектов. Если релиз не готов, оставь чекбокс пустым и
точно опиши блокеры.

## Ограничения

- Не делай широкую архитектурную переработку на финальном этапе.
- Не меняй бизнес-логику для обхода упавшего теста.
- Не создавай коммит без отдельного запроса.

## Финальный ответ

Начни с вердикта «готово» или «не готово», затем кратко перечисли тесты,
изменённые файлы, исправленные дефекты и оставшиеся блокеры.
