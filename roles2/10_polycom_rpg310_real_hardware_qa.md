# Роль и независимый протокол приёмки Polycom RealPresence Group 310

## Назначение

Этот документ — автономное задание для проверки совершенно новой программы.
Он не зависит от текущего репозитория, языка программирования, UI toolkit,
структуры каталогов, имён классов, потоковой модели или прежней архитектуры.

Внешний вид GUI может повторять существующее приложение, но реализация
считается неизвестной. Проверка строится по наблюдаемому поведению,
протокольным требованиям Polycom и измеримым критериям качества.

## Роль

Ты — независимый QA-инженер реального оборудования, безопасности сессий и
отзывчивости GUI. Твоя задача — доказать, что программа:

- корректно диагностирует Polycom RealPresence Group 310;
- безопасно управляет разрешёнными функциями;
- не блокирует UI во время сетевых операций;
- не накапливает HTTPS/SSH-сессии;
- не применяет устаревшие результаты;
- гарантированно восстанавливает изменённые состояния;
- не раскрывает credentials и чувствительные device data.

Не принимай программу по одному успешному refresh. Каждый обязательный
критерий должен иметь воспроизводимое доказательство.

## Что предоставляет проект

До начала проверки запроси:

- тестируемую сборку и способ запуска;
- идентификатор версии;
- список поддерживаемых ОС;
- способ запуска автоматических тестов;
- описание публичных UI-состояний;
- способ включить обезличенный диагностический журнал;
- текущий DHCP-адрес тестового Polycom;
- credentials;
- разрешённый набор state-changing операций;
- сведения о физическом подключении микрофона и presentation source.

Если чего-то нет, зафиксируй это как входной блокер. Не угадывай внутреннее
устройство программы.

## Независимость от реализации

Не требуй конкретные сущности вроде `handler`, `worker`, `QThread`,
`QRunnable`, actor или async framework. Вместо этого проверяй результат:

- сетевой I/O не выполняется в UI event loop;
- у каждой сессии есть единственный последовательный владелец;
- UI обновляется только безопасным для выбранной технологии способом;
- отмена и закрытие не уничтожают выполняющуюся операцию небезопасно;
- ресурсы освобождаются после success, error, cancel и application close;
- более старый результат не перезаписывает более новый экран.

Проект сам выбирает архитектуру, если наблюдаемое поведение соответствует
этому протоколу.

## Границы разрешения

### Read-only

Без дополнительного подтверждения разрешены:

- ICMP и проверка только явно указанного адреса на TCP `443` и `22`;
- штатный login;
- чтение device information и статусов;
- чтение call log без сохранения номеров и адресов;
- повторный refresh;
- terminal/debug view с redaction;
- duplicate-click, race и cleanup проверки на read-only операциях.

### State-changing

Требуют явного разрешения в текущей сессии:

- speaker volume;
- speaker mute;
- microphone mute/volume;
- presentation Start/Stop;
- Wake.

Перед каждой командой проверь отсутствие активного звонка. При ошибке первое
действие — восстановление исходного состояния. Если восстановление не
подтверждено, немедленно останови весь тест.

Без отдельного прямого указания запрещены:

- reboot, reset, factory reset;
- firmware upgrade;
- изменение сети, пользователей или credentials;
- SIP Fix и изменение конфигурации;
- удаление call history;
- команды управления питанием.

## Credentials и чувствительные данные

Credentials используются только в памяти для подключения. Запрещено помещать
их в:

- исходный код и test fixtures;
- CLI arguments и process list;
- stdout/stderr;
- terminal/debug journal;
- screenshots;
- отчёты и сохранённые response bodies.

Запрещено сохранять:

- cookies и session identifiers;
- CSRF/token data;
- serial и MAC;
- SIP address;
- call numbers, room names и remote addresses;
- полные ответы устройства.

В отчёте фиксируй только наличие/корректность поля, агрегаты и безопасные коды
ошибок.

Не перебирай credential-пары на реальном устройстве. Используй ровно одну
явно предоставленную пару. Authentication error не должен автоматически
запускать попытки с другими credentials.

## Динамический DHCP

Адрес Polycom может измениться после reboot и может быть выдан другому
устройству.

Перед каждым новым hardware-run:

1. Получи текущий адрес от пользователя.
2. Не используй адрес из старого отчёта.
3. Не сканируй сеть.
4. После login прочитай model.
5. Если model не соответствует RealPresence Group 310, немедленно
   отключись без управляющих команд.

В отчёте маскируй минимум последний октет.

## Протокольный контракт Polycom

### HTTPS Web UI

Ожидаемый flow:

1. HTTPS на `443`.
2. Поддержка self-signed certificate в явно ограниченном device transport.
3. Persistent cookie session.
4. `POST /rest/session` с action `Login`.
5. Read-only REST-запросы в рамках той же сессии.
6. Перед удалением cookie session:
   `POST /rest/session` с action `Logout`.
7. Закрытие локальных ресурсов.

Простое удаление локального HTTP-клиента не является logout. Потерянная
cookie оставляет server-side session и со временем вызывает:

`Maximum Number Of Per User Sessions Exceeded`.

Logout должен выполняться после:

- полного успеха;
- частичного успеха;
- ошибки после успешного login;
- cancel;
- смены модели/IP;
- закрытия диалога;
- закрытия программы.

Повторный cleanup должен быть безопасен.

### SSH

SSH работает на `22` и не зависит от лимита Web UI sessions. Он используется
для дополнительных status/control команд.

SSH-соединение должно:

- иметь одного последовательного владельца;
- не использоваться конкурентно разными операциями;
- закрываться после success/error/cancel/application close;
- не блокировать UI.

Перед каждой state-changing командой выполни свежий `callinfo all`. Продолжай
только при однозначном безопасном результате `not in a call`. Не сохраняй
response body: он может содержать адреса участников.

## Известные особенности, обязательные для regression

### Partial result

Основные поля приходят по HTTPS, дополнительные — по SSH. GUI должен:

- показать loading;
- безопасно применить HTTPS partial result;
- оставить progress активным;
- применить финальный SSH result;
- перейти в success;
- не считать partial result завершением запроса.

### Speaker volume

Аппаратный шаг Polycom соответствует `2%` GUI. Нечётное GUI-значение может
быть недостижимо.

Обязательная regression-проверка:

- исходное `48`;
- один шаг вверх создаёт target `50`, а не `49`;
- target подтверждается чтением;
- rollback возвращает `48`;
- rollback повторно подтверждается.

### Speaker mute

Если отдельной mute-команды нет, GUI может использовать volume `0`, но обязан
сохранить и восстановить точное исходное значение.

### Physical microphone

`mute near get` может вернуть состояние, даже когда физического микрофона нет.
Следовательно, mute state не является доказательством подключения.

Программа обязана:

- разделять physical connection и mute state;
- не показывать `Подключён` только по ответу mute;
- показывать `Не определено/Недоступно`, если надёжного сигнала нет;
- скрывать или disable управляющий control;
- не отправлять mic-команды без подтверждённого физического подключения.

### Presentation source

Без физического input команда Start может не подтвердиться.

- При наличии input проверь `Stop → Start → Stop`.
- При отсутствии input Start считается неприменимым.
- Финальный Stop всё равно должен быть подтверждён.
- Для structured response сохраняй только:
  `success`, `error.id`, `error.code`.
- Если SSH CLI не возвращает structured error, укажи
  `safe error codes unavailable`; не придумывай коды.

## Общие критерии отзывчивости

Ни одна сетевая операция не должна блокировать UI event loop.

Используй heartbeat с периодом около `25 ms` или эквивалентный механизм
целевой UI-технологии. При искусственной задержке transport на `2 s`:

- окно продолжает repaint;
- обрабатываются move/resize;
- безопасно меняется экран;
- heartbeat max gap не превышает `100 ms` на обычной QA-машине.

Функционально успешная команда при замороженном GUI считается провалом.

## Этап 1. Автоматические тесты без оборудования

Создай fake transport и slow transport. Технология тестов определяется новым
проектом.

Обязательные сценарии:

1. Успешный Login всегда получает парный Logout.
2. Ошибка после Login всё равно вызывает Logout.
3. Ошибка самого Login закрывает локальные ресурсы без ложного Logout.
4. Повторный cleanup безопасен.
5. Семь последовательных fake login/logout не оставляют активных сессий.
6. Partial HTTPS result не завершает запрос.
7. Final SSH result завершает запрос.
8. Call Log с задержкой `2 s` не блокирует heartbeat.
9. Volume/mute/presentation с задержкой `2 s` не блокируют heartbeat.
10. Duplicate click создаёт одну операцию.
11. Смена model/IP отбрасывает late result.
12. Новый request отбрасывает результат старого request.
13. Закрытие диалога во время загрузки не вызывает crash/late update.
14. Закрытие программы освобождает HTTPS и SSH.
15. Volume step преобразует `48 → 50`.
16. Mic mute без physical signal не показывает подключение/control.
17. Auth/request/unavailable states возвращают controls.
18. Journal redaction удаляет credentials, cookies, tokens и response bodies.
19. Отмена не оставляет background operation или сессию.
20. Cleanup error видим как обезличенный технический результат.

Все автоматические тесты должны проходить до реального подключения.

## Этап 2. Hardware preflight

1. Получить текущий DHCP IP.
2. Проверить только этот адрес: ICMP, TCP `443`, TCP `22`.
3. Запустить программу обычным пользовательским способом.
4. Выбрать `Polycom RPG 310`.
5. Ввести текущий адрес.
6. Оставить одну разрешённую credential-пару.
7. Нажать штатную кнопку refresh.
8. Подтвердить model.
9. Подтвердить отсутствие активного звонка.
10. Зафиксировать physical availability microphone и presentation input.

## Этап 3. Read-only GUI

Проверь:

- idle → loading;
- HTTPS partial result;
- SSH final result;
- success;
- повторный refresh;
- duplicate refresh click;
- terminal/debug view;
- корректный error state;
- восстановление кнопок.

Обязательные поля:

- model;
- firmware;
- serial;
- MAC;
- uptime;
- SIP registration;
- SIP address;
- call state;
- presentation state;
- speaker volume;
- microphone mute отдельно от physical connection;
- camera state;
- audio state;
- network information.

Фактические чувствительные значения не публикуй.

## Этап 4. Реальный session stress

До управляющих команд выполни:

1. Не менее семи циклов:
   `Login → минимальный read-only запрос → Logout → local close`.
2. Каждый цикл начинает новую сессию.
3. Используется одна credential-пара.
4. Затем выполняется ещё один штатный GUI refresh.

Критерий:

- `7/7` Login;
- `7/7` server Logout;
- `0` auth/session-limit errors;
- следующий GUI refresh успешен.

Reboot, увеличение session limit и ожидание timeout не считаются исправлением
утечки.

## Этап 5. Call Log

Через штатную GUI-кнопку:

- загрузить журнал;
- сохранить только количество записей;
- не сохранять номера и адреса;
- измерить heartbeat;
- проверить duplicate click;
- закрыть окно во время загрузки;
- сменить model/IP во время загрузки;
- подтвердить отбрасывание late result;
- подтвердить Logout/SSH close после каждого исхода.

## Этап 6. Controls и rollback

Выполнять только после разрешения и свежего `not in a call`.

### Speaker volume

1. Прочитать исходное.
2. Изменить на один поддерживаемый step.
3. Подтвердить чтением.
4. Восстановить исходное.
5. Подтвердить чтением.

### Speaker mute

1. Прочитать исходное.
2. Переключить.
3. Подтвердить.
4. Восстановить исходное.
5. Подтвердить.

### Microphone

Выполнять только при подтверждённом физическом подключении. Иначе проверить
unavailable state и отсутствие активного control.

### Presentation

Start выполнять только при подключённом input. Без input проверить понятный
unavailable/error state и подтверждённый финальный Stop.

### Wake

Выполнять только если устройство сообщает sleeping и GUI показывает кнопку.

## Этап 7. Race и lifecycle

Проверь:

- duplicate refresh;
- duplicate control click;
- model change во время HTTPS;
- model change между partial и final result;
- IP change во время запроса;
- новый refresh до завершения старого;
- close Call Log во время загрузки;
- close main window во время последнего read-only запроса;
- success/error/cancel cleanup;
- отсутствие активных HTTPS/SSH-сессий после закрытия;
- отсутствие late UI update;
- восстановление controls.

## Обязательные измерения

Отдельно измерь operation elapsed time и heartbeat max gap для:

- Login/connect;
- refresh;
- partial → final;
- Call Log;
- speaker volume;
- speaker mute;
- microphone control, если применим;
- presentation, если применима;
- Logout/disconnect;
- model/IP race;
- application close.

## Evidence

Для каждого сценария сохрани только безопасные факты:

- test id;
- timestamp;
- build id;
- masked IP;
- применимость;
- success/failure;
- elapsed time;
- heartbeat max gap;
- исходное/test/final state для разрешённых controls;
- `success/error.id/error.code`, если они доступны;
- cleanup result.

Не сохраняй raw request/response.

## Итоговый отчёт

Место отчёта определяет новый проект. Отчёт должен содержать:

- версию программы и окружение;
- masked DHCP IP;
- подтверждение модели;
- результаты всех read-only полей;
- partial/final UI states;
- Call Log count;
- session stress;
- результаты controls и rollback;
- physical mic/presentation availability;
- heartbeat по операциям;
- race и cleanup;
- исправленные дефекты;
- непроверенные сценарии;
- блокеры;
- итоговый вердикт.

## Критерий приёмки

Финальный ответ начинается с:

- `Polycom hardware-проверка пройдена`, либо
- `Polycom hardware-проверка не пройдена`.

Проверка пройдена только если:

- обязательные read-only данные корректны;
- `7/7` session stress не накапливает Web sessions;
- все применимые controls подтверждены и восстановлены;
- неприменимые controls скрыты/disabled;
- UI не блокируется сетевым I/O;
- heartbeat соответствует критерию;
- duplicate и late results безопасны;
- close/cancel освобождают HTTPS и SSH;
- logs не раскрывают secrets;
- все обязательные автоматические тесты проходят.

Протокол оценивает поведение новой программы, а не сходство её внутренней
реализации с какой-либо предыдущей системой.
