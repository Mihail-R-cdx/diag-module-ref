## Context

The current equipment-inventory pipeline intentionally separates offline Excel ingestion
from normal runtime diagnostics. The primary workbook is converted into an immutable
versioned JSON snapshot, and an optional network workbook enriches switch-connection
metadata by canonical MAC.

Current generated versions are mode-dependent:

```text
primary workbook only                 -> schema v2
primary + valid network workbook      -> schema v3
```

Schema v2 adds `room_vip`; schema v3 adds `switch_ip_address` and `switch_port`. The source
workbook also contains `Адрес комнаты`, but that value is not represented in the canonical
snapshot. The upcoming room-equipment diagnostic tree requires the address as room display
metadata and benefits from a single current record shape independent of import mode.

The current root specification also defines importer consistency diagnostics for room
display disagreement, including conflicting `room_name` and `room_vip` values under one
`room_id`. The approved direction is that `room_id` alone identifies a room. Display
metadata stays attached to individual records; the importer does not reconcile or choose a
room-wide value. A later room-orchestration change will define how one concrete room session
selects display values from those records.

## Goals

- Preserve `Адрес комнаты` as nullable canonical `room_address`.
- Make schema v4 the only schema generated by the current importer, with one exact record
  shape for both one-source and two-source conversion.
- Keep valid schema v1, v2, and v3 deployment snapshots loadable without rewriting them.
- Preserve current network-source configuration, MAC-only reconciliation, atomic
  publication, deterministic identity, and deployment-data isolation.
- Remove importer authority to classify differing room display metadata within one
  authoritative `room_id` as a conflict.
- Keep the change inventory-only so the later room-tree orchestration can build on a stable
  approved data contract.

## Non-goals

- No room-equipment tree or accordion UI.
- No source-IP room resolution or room-cycle orchestration.
- No change to device diagnostic dispatch or the supported-model registry.
- No new PDU-to-codec enrichment or related-device network I/O.
- No live polling, local-refresh, auxiliary-read, state-changing, or cleanup lifecycle
  changes.
- No credential storage or fallback changes.
- No Excel parsing in normal application runtime.
- No automatic file watching or hot reload of `equipment_inventory.local.json`.
- No new authority for `room_name`, `room_address`, or `room_vip` to identify or merge rooms.

## Decisions

### 1. Schema v4 is the single current publication format

Every successful new conversion publishes `schema_version = 4`, regardless of whether the
optional network source is configured.

```text
primary only
    -> schema v4
    -> switch_ip_address = null
    -> switch_port = null

primary + configured valid network source
    -> schema v4
    -> switch fields populated only by the existing MAC-only reconciliation contract
```

This removes schema selection as an import-mode concern while preserving the optional
network source itself. If a network source is configured and fails its approved
configuration/read/layout contract, the run remains fatal; the importer must not pretend the
network source was absent and publish a primary-only candidate.

### 2. Exact schema-v4 record shape

A schema-v4 record contains exactly:

```text
record_id
source_model
diagnostic_model
ip_address
mac_address
serial_number
room_id
room_name
room_address
device_kind
room_vip
switch_ip_address
switch_port
```

Required non-null fields remain:

```text
record_id
device_kind
```

All other record fields are nullable under their existing canonical normalization rules.
`room_address` uses canonical nullable text normalization: Unicode NFC, trim leading and
trailing whitespace, preserve case/internal text, and convert empty normalized text to
null.

`room_address`, `room_vip`, `switch_ip_address`, and `switch_port` are present as keys in
every schema-v4 record even when null. V4 does not permit hybrid record shapes.

### 3. `Адрес комнаты` is a required source header but a nullable row value

The exact primary-workbook header is:

```text
Адрес комнаты -> room_address
```

The header is mandatory for the current importer and primary-source preflight. Missing or
ambiguous discovery of that semantic column is a fatal source-structure issue. Conversion
must preserve any previous valid output.

An individual empty address cell is not a source-structure error and does not make the row
fatal. It becomes `room_address = null`.

No aliases, fuzzy header matching, or inferred address source are introduced.

### 4. Historical schema versions remain strict and loadable

The runtime loader continues to validate the exact declared source-version shape and
identity before adaptation:

```text
schema v1
    -> room_vip = null
    -> room_address = null
    -> switch_ip_address = null
    -> switch_port = null

schema v2
    -> room_vip read
    -> room_address = null
    -> switch_ip_address = null
    -> switch_port = null

schema v3
    -> room_vip read
    -> room_address = null
    -> switch_ip_address read
    -> switch_port read

schema v4
    -> room_vip read
    -> room_address read
    -> switch_ip_address read
    -> switch_port read
```

Adaptation occurs only after the source version has passed its own strict shape and
snapshot-identity checks. The loader does not rewrite the source file. Extra, missing, or
hybrid fields in a declared supported version are `INVALID_SNAPSHOT`; undeclared future
versions remain `UNSUPPORTED_SCHEMA`.

### 5. V4 identity includes room address and the complete v4 record

The deterministic identity algorithm remains conceptually unchanged:

```text
snapshot_id = "sha256:" + sha256(canonical identity payload)
identity payload = {schema_version, records}
```

Records remain sorted by canonical `record_id`, JSON object keys remain deterministic, and
generation/report metadata stays outside identity. Because `room_address` is part of each
schema-v4 record, an address change changes `snapshot_id`. The same remains true for all
other canonical record fields, including nullable switch fields.

### 6. Room identity and display metadata have separate authority

`ID комнаты`/`room_id` remains the only room identity authority. `room_name`,
`room_address`, and `room_vip` are per-record display metadata.

For schema-v4 import the importer:

- preserves normalized display values on every record;
- does not compare records sharing one `room_id` to decide whether their display values
  conflict;
- does not emit `ROOM_NAME_CONFLICT`, `ROOM_VIP_CONFLICT`, or a new
  `ROOM_ADDRESS_CONFLICT` merely because records under one `room_id` differ;
- does not choose or rewrite a room-wide display value;
- does not merge rooms by display metadata.

This change deliberately does not redefine the existing GUI/runtime room-display
aggregation. The later `room-equipment-diagnostic-tree` change will define source-record
and canonical-order selection for the new room session UI. The v4 importer simply removes
cross-record display reconciliation from its publication authority.

### 7. Network enrichment semantics remain unchanged except for candidate version

The network workbook remains optional and keeps the exact current contract:

```text
worksheet: Устройства
MAC-адрес       -> MAC-only join evidence
IP коммутатора  -> switch_ip_address candidate
Порт            -> switch_port candidate
```

`Изменения` and `Корректная запись` remain ignored. Existing ambiguity, partial-candidate,
invalid-field, and unmatched-MAC semantics remain unchanged. The only versioning change is
that a successful enriched candidate is schema v4 rather than schema v3.

Combined preflight likewise builds and validates a schema-v4 candidate in memory and does
not publish it.

### 8. Publication remains fail-closed and atomic

The importer still builds the complete candidate, computes its deterministic identity, and
validates it through the runtime loader before replacing the configured output. Fatal
primary-source structure failures, fatal configured-network failures, invalid candidates,
or publication failures leave the previous valid snapshot untouched.

Real workbooks and `equipment_inventory.local.json` remain deployment-local and untracked.
Tests use only synthetic inventory.

## Migration and compatibility

No in-place migration of deployment snapshots is required. Existing valid v1-v3 files can
continue to load. To obtain `room_address` and the unified record shape, operators rerun the
offline importer against the current primary workbook containing the required
`Адрес комнаты` column. The newly generated output is schema v4.

No code in this change reads `.xlsx` during application startup or diagnostic operations.

## Validation strategy

Implementation must add synthetic regression coverage for at least:

- primary-only conversion publishes schema v4 with null switch fields;
- two-source conversion publishes schema v4 with reconciled switch fields;
- exact `Адрес комнаты` header maps to `room_address`;
- blank address cell becomes null;
- missing or ambiguous address header is fatal and preserves previous output;
- v4 record missing any declared key is invalid;
- v4 record with an extra undeclared key is invalid;
- room-address changes alter v4 `snapshot_id`;
- valid v1/v2/v3 snapshots still load and expose `room_address = null`;
- mixed `room_name`, `room_address`, or `room_vip` values under one `room_id` do not create
  importer room-display conflict issues and do not drop or rewrite records;
- configured network failure does not downgrade to primary-only publication;
- combined preflight reports schema version 4 and publishes nothing;
- normal runtime inventory loading remains independent of spreadsheet libraries.

Focused inventory/importer tests, the full offline test suite, strict change validation,
strict all-artifact validation, and Git whitespace checks remain required during
implementation and independent validation.

## Risks and trade-offs

### One schema version for both import modes

The v4 record is slightly wider for primary-only deployments because switch keys are always
present as null. This is intentional: stable shape is more valuable for downstream room
orchestration than saving two nullable keys.

### Removal of importer room-display conflict diagnostics

The importer will no longer warn that records sharing one `room_id` disagree on
`room_name` or `room_vip`, and it will not warn about differing addresses. This follows the
approved authority model: those fields are display metadata, not identity. The data remains
fully observable on individual records, so later application logic can select a display
value without losing source multiplicity.

### Backward loading complexity

Supporting four exact schema shapes adds loader branches, but avoids forcing an operational
snapshot migration before the application can start. Strict per-version validation prevents
that compatibility layer from accepting malformed hybrids.

## Follow-on changes

The intended next changes are:

1. `room-equipment-diagnostic-tree` — source-IP room resolution, per-record room state,
   sequential one-shot diagnostics, and the equipment tree UI.
2. `room-device-interaction-lifecycle` — post-cycle live behavior, local refresh,
   auxiliary read actions, state-changing operations, and lifecycle handoff/cleanup.

Those changes consume schema v4 but must not reopen or silently alter the inventory
contracts approved here.
